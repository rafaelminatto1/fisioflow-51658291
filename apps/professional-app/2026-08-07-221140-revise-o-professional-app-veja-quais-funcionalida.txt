     1.1 Migration 0165_biomechanics_pose_provenance.sql (+ .down.sql)

     Espelhar em packages/db/src/schema/biomechanics.ts. Todas as tabelas estão

     - biomechanics_metrics += provenance NOT NULL DEFAULT 'synthetic_demo'

     - biomechanics_frames/_events += provenance, attempt/view, job_id,

     - biomechanics_jobs += phase ('device'|'container'), input_digest,
     supersedes_job_id + índice único (assessment_id, phase, input_digest).
     - biomechanics_assessments += pose_provenance, amends_assessment_id,
     superseded_by_assessment_id, locked_at; CHECK de status ampliado.
     - Dois triggers (última linha de defesa, valem mesmo se a API for
     contornada): trg_bio_block_synthetic_on_signed impede status='signed' com

     1.2 packages/core/src/biomechanics/ — cinemática pura (TDD, antes de 
     qualquer fiação)

     packages/core já é dependência de apps/api e de apps/professional-app — o
     número que o app desenha no overlay e o que a API grava no laudo saem da
     mesma função.

     Arquivos: landmarks.ts (índice canônico BlazePose-33 + adapters
     MLKit/AppleVision/MediaPipe + applyCoordinateSpace), math.ts, kinematics.ts
     (ROM, valgo FPPA, inclinação de tronco, queda pélvica, índice de simetria,
     cadência), events.ts, quality.ts, pipeline.ts, provenance.ts, ndjson.ts.

     Função única por onde tudo passa — sem env, sem fetch, sem Date.now():
     computeAssessmentMetrics({ header, frames, protocol, provenance,
     algorithmVersion })
       : { metrics, events, keyframes, quality, rejected }
     Consciência de plano é obrigatória: valgo/queda pélvica só de
     view==='frontal'; flexão sagital só de 'sagittal'. Plano incompatível,
     usableFrameRatio < 0.6 ou score < 0.5 no pico ⇒ não emite métrica, emite
     RejectionReason. "Não mensurável nesta captura" é melhor que um número
     plausível e errado.

     1.3 Contrato de dados ff-pose-33-v1

     NDJSON gzip, uma linha por frame, structure-of-arrays:
     {"i":42,"t":1400,"k":[x,y,z,score × 33],"c":0.88}. Linha 0 é o header com
     fps, view, attempt, poseEngine, device, calibration e coordinateSpace 
     (mirrored, rotationDegrees) — sem isso a câmera frontal troca Esq/Dir em
     todo o laudo.

     Tamanho: 10 s @30 fps ≈ 270 KB cru / 45–60 KB gzip. Vai bem pela rede; não
     vai como 9.000 linhas no Postgres via Hyperdrive. Por isso: bundle inteiro

     Sem esta fase, todo usuário Android sem o plugin linkado e toda sessão em

     txt} + apps/api/src/containers/BiomechanicsPoseContainer.ts.
     - wrangler.toml: [[containers]] com instance_type = "standard-4" (4 vCPU /
     12 GiB — limites confirmados na doc atual da Cloudflare; custom instance
     types também disponíveis desde jan/2026), max_instances = 5, DO binding
     BIOMECHANICS_POSE, [[migrations]] tag = "v16" com new_sqlite_classes (a
     base Container exige DO com SQLite).
     - Justificativa do porte: ffmpeg decode de clipe 1080p 10–30 s + N passes
     de pose. Em 4 vCPU com batch de 32 frames dá ~12 s no caso comum e ~45–70 s
     no pior; abaixo disso dobra a latência para economizar ~25% — trade errado
     numa ferramenta cujo valor é "o número do laudo é real".
     - O Worker não streama o vídeo por si: gera presigned GET (15 min) do R2 +
     presigned PUT para o resultado, chama o DO, e o container devolve o mesmo 
     ff-pose-33-v1. Callback autenticado por HMAC (POST 
     /api/biomechanics/internal/jobs/:jobId/pose-callback, fora do router
     org-scoped, usando createPoolForOrg).
     - O Worker calcula as métricas, não o container — o container é um extrator
     de pose e nada mais. Uma implementação de matemática clínica, uma suíte de
     testes.

     Política de laudo assinado (decisão clínica, explícita)

     Laudo assinado é imutável. Reprocessamento nunca o altera.
     1. O container só roda automaticamente enquanto status ∈ 
     {awaiting_landmarks, needs_review} — nunca em varredura de fundo sobre
     laudo assinado.
     2. Reprocessamento pedido sobre um assinado cria nova avaliação
     (amends_assessment_id), reaproveitando o vídeo no R2. report_hash,
     signed_at e o PDF original nunca mudam → /verify do original continua
     valid:true para sempre.
     3. Detecção de divergência: diferença acima do limiar clinicamente
     relevante (>5° angular, >5 p.p. simetria, >8 spm cadência) grava
     biomechanics_review_actions(action='reprocess_discrepancy') e notifica quem
     assinou. Silêncio aqui seria o pior desfecho possível.
     4. É retificação, não sobrescrita: o PDF novo declara "Retifica o laudo X
     de <data>"; a página pública do original passa a informar supersededBy. Os
     dois documentos permanecem recuperáveis.

  - Rollback não atravessa a mudança. Você não consegue voltar para uma versão
  anterior à conversão.
  - É mutuamente exclusivo com migrations — não dá para testar meio a meio.

  Converter para exports, mas com você presente e ciente de que é irreversível,
  e num momento em que uma eventual indisponibilidade seja aceitável. Não é uma
